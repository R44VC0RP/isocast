# Build an agent-native OBS, don't port one

Nobody has yet built a mature Rust OBS, and nobody has built a broadcast engine designed for AI agents from the ground up. Every self-described "OBS in Rust" (Rivulet, GodwinMix, ROBS, rec-rs) appeared in 2025–2026, has fewer than 10 GitHub stars, and is alpha or abandoned. The serious Rust prior art sits next to that goal rather than on it. **Smelter** (Software Mansion) is a production-grade wgpu live compositor with a declarative scene tree, but it has no desktop capture and its licence forbids bundling it into a distributed app without a deal starting at $1,000/month. **Cap** (~23k stars) is a polished recorder that shows how to structure capture and encode crates per platform. **libobs-rs** wraps the real libobs, but it is GPL-3.0 and does not work on macOS. On the control side, every "AI controls OBS" project in 2025–2026 is a thin MCP wrapper around obs-websocket v5. Those wrappers inherit OBS's imperative, name-addressed model, have no rollback, and have no dependable way to show the model what is on air. The Rust crate ecosystem is strong for capture, GPU compositing, and WebRTC/WHIP. It is weak or stale for audio mixing, RTMP, SRT, AMD/Intel hardware encoders, and zero-copy encode, so those parts get built or bridged through FFmpeg or GStreamer. The recommended path has four parts. Write a clean-room, headless Rust core around a versioned, declarative scene document. Use permissively licensed per-OS capture crates and wgpu. Use FFmpeg (LGPL build) or GStreamer as the encode and output back end. Expose one method table over REST, WebSocket, CLI, and MCP, with plan/apply, preview frames, and Preview→Program safety built in. Before writing the engine, prototype the agent layer against stock OBS through `obws`, which is fast and keeps the licences separate.

## Every Rust OBS rewrite so far is a months-old alpha

Searching GitHub for Rust OBS replacements turns up a cluster of very young projects. Their feature lists are README claims; none of them were run for this research. **Rivulet** is the most ambitious. It once described itself as "a complete Rust reimplementation of OBS Studio" and now calls itself "an embeddable, deterministic recording & streaming engine". It has crates for a semver-stable `rivulet-core`, WASM plugins, an OBS plugin-compat layer, and an `rivulet-obs-websocket` compatibility crate. It is MIT-licensed, has 3 stars, and is tagged `v0.65.0-alpha.283` with several alpha tags per day ([GitHub](https://github.com/thoser666/rivulet), [README](https://github.com/thoser666/rivulet/blob/develop/README.md), [releases](https://api.github.com/repos/thoser666/rivulet/releases)). **GodwinMix** is the most agent-oriented. It describes itself as "Headless core, web UI, desktop app, MCP for agents", is Apache-2.0, has 7 stars, and was created in September 2026. Media runs on GStreamer, and one method table is served over JSON-RPC WebSocket, REST, MCP stdio, and plugins ([README](https://github.com/psmux/GodwinMix), [protocol.md](https://raw.githubusercontent.com/psmux/GodwinMix/main/protocol.md)). **ROBS** ("a complete rewrite of OBS Studio in Rust") stopped after 14 commits in April 2026, with chat still "simulated" ([GitHub](https://github.com/Signal-Six/ROBS)). **rec-rs** is a macOS-only recorder built on ScreenCaptureKit, AVFoundation, CoreImage, and VideoToolbox, with no scenes or streaming. Its README says it was built by studying OBS "with REA and Claude Code" ([README](https://github.com/michaelshimeles/rec-rs)).

The rapid release cadence and very large docs of these projects suggest they are mostly AI-assisted builds. Treat them as idea sources, not foundations. Two patterns hold across all of them. First, they hand media to an existing framework (GStreamer for Rivulet, GodwinMix, Kooha, and Framepipe; FFmpeg for Cap and Videorc) rather than writing codecs. Second, the abandoned efforts (ROBS, the archived `rust-obs-plugins`, the stalled `obs-shaderfilter-plus`) stalled on OBS's sheer surface area, not on Rust ([GitHub API search](https://api.github.com/search/repositories?q=OBS+rust)).

The more mature projects each cover one slice of the problem:

| Project | What it proves | Licence | Why it is not "the" answer |
|---|---|---|---|
| [Smelter](https://github.com/software-mansion/smelter) (~700–735★, v0.6.0 June 2026) | wgpu compositor, declarative component tree per output, HTTP API + React/Python SDKs, CEF web source, Vulkan Video zero-copy, DeckLink, WHIP/RTMP/HLS/MoQ | Custom; real-time use is free only for organizations with ≤50 employees and <10k concurrent viewers; bundling into a distributed app needs a commercial licence from $1,000/month ([LICENSE](https://github.com/software-mansion/smelter/blob/master/LICENSE)) | Server-side only: no screen, window, or game capture and no operator UI |
| [Cap](https://github.com/CapSoftware/Cap) (23,213★) | Per-OS capture/camera/encoder crates (`scap-screencapturekit`, `scap-direct3d`, `camera-mediafoundation`, `enc-avfoundation`…), wgpu, Tauri | GitHub reports NOASSERTION | Recording plus editing, no live scenes or streaming ([crates/](https://api.github.com/repos/CapSoftware/Cap/contents/crates)) |
| [Videorc](https://github.com/TheOrcDev/videorc) (498★) | Rust backend owning capture, composition, recording, and RTMP simulcast behind an authenticated localhost WebSocket, with an Electron UI | AGPL-3.0 | Mac beta, no releases |

Smelter deserves extra attention because its API is the clearest existing model for an agent-drivable compositor. Inputs, outputs, and resources (shaders, images, web renderers, fonts) are registered by ID. Each output carries a scene, which is a tree of `View`, `Rescaler`, `Tiles`, `Text`, `Image`, `InputStream`, `Shader`, and `WebView` components. Changes arrive as a whole-tree replacement through `POST /api/output/:id/update`, optionally timed with `schedule_time_ms` ([HTTP API](https://smelter.dev/http-api/overview), [routes](https://smelter.dev/http-api/routes)). Its React SDK uses `react-reconciler` to compile JSX into that native GPU scene graph. LiveKit Egress and Daily VCS, by contrast, run React in headless Chromium ([Software Mansion blog](https://swmansion.com/blog/the-missing-layer-in-live-video-streaming-ap-is-programmable-video-composition)). Smelter also ships Agent Skills that are evaluated against eval files before merging ([smelter-labs/skills](https://github.com/smelter-labs/skills)). The licence means you can study and copy Smelter's ideas but should not depend on its code for a distributed desktop product.

## Rebuilding libobs means rebuilding eight subsystems and fixing its known flaws

libobs is a C runtime built around one global context. Its core is a polymorphic, reference-counted source graph: inputs, filters, transitions, and scenes are all "sources", and scenes and transitions are composite ([Source API](https://docs.obsproject.com/reference-sources)). The runtime has three threads: graphics, video output, and audio. The graphics thread composites the channels to a texture, converts it (usually to YUV), and queues it. **When the queue is full it duplicates the last frame**, which is where "skipped frames due to encoding lag" comes from. The audio thread ticks every **1024 samples (~21 ms at 48 kHz)**. On each tick it pulls the timestamp-nearest audio from each source's ring buffer, mixes up the tree through each parent's `audio_render`, and feeds the encoders. An interleave queue then emits packets in monotonic timestamp order ([Backend Design](https://docs.obsproject.com/backend-design)). Settings use a JSON-backed `obs_data` plus `obs_properties` UI schemas. Outputs, encoders, and services are plugin types. Since 31.1, an **unstable** canvas API generalizes the single main mix into several, all sharing one global frame rate ([Canvas API](https://docs.obsproject.com/reference-canvases)).

A from-scratch engine therefore needs eight things:

1. A typed source graph with activate/show reference counting.
2. A per-canvas compositor.
3. Colour conversion (NV12/P010, Rec.709/2100, range, HDR).
4. Base-to-output scaling.
5. A fixed-tick, timestamped audio mixer with resampling.
6. Encoder, output, and service abstractions with packet interleaving.
7. A settings schema that can drive generic UIs.
8. Optionally, a scene-collection serializer for importing OBS JSON. Scenes are sources with `"id":"scene"` whose items carry `source_uuid` and transforms ([obs-json-reference](https://github.com/MrDemonWolf/obs-setup/blob/main/docs/obs-json-reference.md)).

The object model is the easy part. The hard engineering is timing and GPU interop.

OBS's own history lists the flaws a rewrite can fix:

- **No headless mode.** The 2018 "headless mode with full API control" idea is marked **Declined** ([OBS Ideas #16](https://ideas.obsproject.com/posts/16/add-a-headless-mode-that-allows-full-control-via-scripting-api)).
- **One process-global context.** libobs is a singleton ([obs.h](https://github.com/obsproject/obs-studio/blob/master/libobs/obs.h)), and portable multi-instance mode is Windows-only ([KB](https://obsproject.com/kb/portable-mode)).
- **Saving belongs to the Qt frontend, not the core** ([32.1 notes](https://obsproject.com/blog/obs-studio-32-1-release-notes)).
- **A graphics layer shaped around D3D11.** The original author wrote that he "probably should have used something like ANGLE" ([Rendering Graphics](https://docs.obsproject.com/graphics)). The 2025 Metal port had to re-add D3D-style implicit behaviour because "the core renderer was not available for a rewrite" ([OBS blog](https://obsproject.com/blog/obs-studio-gets-a-new-renderer)).
- **Sync heuristics with long-standing failure modes.** A buffered async video source can drift "always increasing… and it will never be resynched back" ([Discussion #11142](https://github.com/obsproject/obs-studio/discussions/11142)). Dynamic audio buffering grows until sources stop working ([forum](https://obsproject.com/forum/threads/video-audio-drift.130841)).
- **No per-source (ISO) recording.** It has been "Planned" since 2018 ([forum](https://obsproject.com/forum/threads/plugin-development-canvas-api-over-obs-websocket-vendor-requests-and-iso-recording-plans.196332)).

A Rust design that fixes these follows directly:

- an instance-scoped engine with no globals
- a library-first daemon where the GUI is just another client
- wgpu with WGSL instead of a custom effect transpiler
- one monotonic master clock with explicit drift correction instead of accumulating offsets
- N canvases, each with its own frame rate, from day one
- ISO recording as a first-class output

The price is OBS's ten-year long tail of capture sources, game-capture hooks, encoders, and protocols.

## Crates cover capture and WebRTC well; mixing, RTMP, SRT and zero-copy encode stay DIY

No single cross-platform capture crate is both current and production-grade. `scap` has had no push since August 2025, and `xcap` is screenshot-focused, with Wayland and window recording incomplete ([scap](https://github.com/CapSoftware/scap), [xcap](https://github.com/nashaofu/xcap)). The working pattern, which Cap follows, is one native backend per OS behind your own trait. The table summarizes the reuse-versus-build decision by layer, using crates.io and GitHub data from October 11, 2026.

GStreamer is the one foundation that closes most of these gaps at once. Its Rust bindings ([`gstreamer`](https://crates.io/crates/gstreamer) 0.25) and Rust-written plugins are first-class parts of the project. Those plugins include `webrtcsink` with congestion control, `whipclientsink`, `isofmp4mux`, `hlssink3`/CMAF, NDI, `gopbuffer` for replay buffers, `audiornnoise`, `audioloudnorm`, and `intersink`/`intersrc` for passing streams between pipelines. Platform elements cover DXGI/WGC capture, WASAPI process loopback, and PipeWire. A pipeline-global `GstClock` handles A/V sync ([gst-plugins-rs](https://github.com/GStreamer/gst-plugins-rs), [sync design](https://gstreamer.freedesktop.org/documentation/additional/design/synchronisation.html)). The costs are shipping a large C runtime on macOS and Windows (gstreamer-rs warns off Homebrew on macOS), caps-negotiation debugging, careful pad-blocking for live scene edits, and memory types that are not wgpu textures ([gstreamer-rs](https://github.com/GStreamer/gstreamer-rs)).

The right split mirrors OBS's own separation of libobs rendering from FFmpeg-based outputs. Own the scene graph, wgpu compositor, clock, and mixer. Use GStreamer (via `appsrc`) or FFmpeg for encoding and transport. In Rust you must also build the clock layer yourself. None of the capture crates offer a cross-source clock-domain abstraction, so every timestamp (ScreenCaptureKit PTS, WGC `SystemRelativeTime`, PipeWire metadata, WASAPI QPC) has to be mapped into one monotonic timebase. After that, drift is corrected with an adjustable-ratio resampler, video is paced at a constant rate by duplicating or dropping frames, and packets are interleaved by DTS before muxing.

## Licensing narrows the options to clean-room code plus permissive crates

OBS Studio and libobs are **GPL-2.0-or-later**. The OBS Project states that "any proper plugin that links with OBS Studio is subject to the GPL", and it restricts use of the OBS name and logo ([README](https://github.com/obsproject/obs-studio), [IP policy](https://obsproject.com/forum/threads/forum-resource-and-ip-policy.178569)). The FSF treats dynamic linking and shared address space as forming a combined work. It treats pipes and RPC between separate programs as generally separate works, and it says shared memory carrying complex data structures is "pretty much equivalent to dynamic linking" ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#GPLPlugins)). Four paths follow; this is not legal advice.

**Embedding libobs** via libobs-rs (GPL-3.0) makes your app effectively GPL-3.0, and it currently excludes macOS. **Driving a stock OBS process** over obs-websocket (GPL-2.0 itself) keeps the controller under any licence by the usual reading, but no court ruling or OBS statement settles it. A shared-memory or texture-sharing bridge into OBS weakens that separation. **A clean-room rewrite** is not bound by the GPL, provided no OBS source is copied, including HLSL effect files. One caution: rec-rs describes itself as "clean-room" while also saying it was built by studying OBS, which is not clean-room in the strict sense. Keep an auditable separation between people (or agents) who read OBS source and those who write engine code; use the published docs and protocol spec as the reference. **Building on Smelter** needs a commercial licence for any distributed desktop app or programmatic-video SaaS ([LICENSE](https://github.com/software-mansion/smelter/blob/master/LICENSE)).

The surrounding stack mostly fits a permissive engine. wgpu, cpal, rubato, screencapturekit, windows-capture, ashpd, pipewire, str0m, webrtc-rs, and cef-rs are MIT or Apache. FFmpeg and GStreamer licensing depends on build configuration, and Videorc bundles an LGPL FFmpeg build specifically ([Videorc README](https://github.com/TheOrcDev/videorc)). Copyleft risks to avoid importing casually are Kooha and Framepipe (GPL-3.0), Videorc and `obs-irl-source` (AGPL), and `dxgcap` (AGPL). Cap's NOASSERTION licence means its crates are a reference to study, not a dependency to take without checking.

## Today's OBS agents are thin websocket wrappers with no undo and no eyes

obs-websocket v5 is the substrate for every OBS agent integration. It provides JSON or MsgPack RPC with Hello/Identify/Request/Event/RequestBatch opcodes, bitmask event subscriptions (high-volume events are opt-in), and vendor requests for plugin extensions. Its best primitive is `RequestBatch` with **`SerialFrame` execution**, which runs requests "in sync with the graphics thread" with `sleepFrames` delays. Batches have **no rollback**: `haltOnFailure` simply stops ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)). Its gaps matter for agents. It cannot create canvases, it cannot set bitrate in Advanced output mode ([#12925](https://github.com/obsproject/obs-studio/issues/12925)), and `GetSourceScreenshot` renders a source rather than the real Program output, so in Studio Mode it can disagree with what is on air ([#1130](https://github.com/obsproject/obs-websocket/issues/1130), [#1257](https://github.com/obsproject/obs-websocket/issues/1257)). From Rust, [`obws`](https://docs.rs/obws/latest/obws/index.html) 0.15 (MIT) is the mature client and includes a canvases module.

The community OBS MCP servers fall into two camps. One camp is exhaustive one-to-one wrappers, such as [xDarkzx/OBS_MCP](https://github.com/xDarkzx/OBS_MCP) with 148 tools. The other is curated, intent-level surfaces, such as [aaronckj/obs-studio-mcp](https://mcprepository.com/aaronckj/obs-studio-mcp) with roughly 30 tools and `dry_run=true` on every mutating call. The best ideas in the second camp are domain-expert pipeline tools. `clean_audio_input` builds a Noise Gate → RNNoise → Compressor chain using parameter keys verified against OBS's filter source. `diagnose_av_health` reads render skips as GPU problems, output skips as encoder problems, and congestion as bitrate problems. Visual feedback is the unsolved piece. A YC hackathon team reported that they "could not make it providing screenshot to claude via MCP" ([yshk-mrt/obs-mcp](https://github.com/yshk-mrt/obs-mcp)), and no surveyed server returns a rendered Program frame as MCP image content. Adjacent gear shows the same pattern. An [ATEM MCP](https://github.com/guycochran/atem-mcp-server) wraps switcher commands. [Restream's official MCP](https://developers.restream.io/mcp-server) uses OAuth 2.1 scopes, deliberately leaves out some capabilities, and tells users to keep human confirmation on for write calls. No reliability or latency data exists for any of these servers.

Two counter-signals argue against making MCP the only interface. Bitfocus Companion's maintainers rejected MCP in 2026. They cited arbitrary-shell reach, data flowing to the LLM provider, and context pollution ("LLMs are much better at using the cli (e.g. curl) or writing small scripts"), and chose to build a clean REST API instead ([companion#3945](https://github.com/bitfocus/companion/discussions/3945)). Remotion deprecated its MCP in favour of Agent Skills ([Remotion](https://www.remotion.dev/docs/ai/mcp)), and Smelter ships Skills with evals. Elsewhere in agent-driven media, the best design guidance comes from Vedal's **Neuro SDK** for games ([BEST_PRACTICES](https://github.com/VedalAI/neuro-sdk/blob/main/API/BEST_PRACTICES.md)):

- Keep the action set stable, because changes slow the model.
- Use enums for fixed choices.
- Avoid near-duplicate actions, which the model fixates on.
- Validate, acknowledge, then execute.
- Return failures that list the valid options.
- Send occasional meaningful context instead of telemetry spam.

AI-streamer stacks such as MOLTSTREAM and EchoBot treat OBS as a dumb output, driven from a fast chat→LLM→TTS loop plus a slower "director" or schedule ([MOLTSTREAM](https://moltstream.app/), [EchoBot](https://github.com/Xyber-Labs/EchoBot)). An engine should therefore expect several controllers working at different timescales.

## Recommended architecture: one headless core, one method table, four front doors

The evidence converges on a specific shape. GodwinMix already shows the protocol half of it: a media-free `protocol` crate and one method table served over JSON-RPC, REST, and MCP. Every call takes `dry_run` (which returns a diff), an `idempotency_key`, `confirm` tokens for destructive methods, a `trace_id`, and token scopes ([protocol.md](https://raw.githubusercontent.com/psmux/GodwinMix/main/protocol.md)). Smelter shows the state half: a declarative tree per output, replaced wholesale and diffed internally, schedulable by timestamp. CasparCG AMCP contributes `LOADBG` for staging content behind the live layer, the `CG ADD → PLAY → NEXT → STOP → REMOVE` graphics lifecycle, and `PRINT` for still frames ([AMCP](https://www.casparcg.com/docs/wiki/protocols/amcp-protocol)). Daily VCS contributes video-clock time instead of wall-clock time, which makes live and offline renders identical ([VCS best practices](https://docs.daily.co/reference/vcs/core-concepts/best-practices)).

The engine should be organised as a Cargo workspace with these layers:

| Crate | Responsibility | Built on |
|---|---|---|
| `*-protocol` | Typed scene document, method table, JSON Schema/OpenAPI; no media dependencies | `serde`, `schemars`, `utoipa` (Smelter's choice) |
| `*-core` | Scene document → reconciler → render graph; master clock; canvases at independent frame rates; audio mixer; revisions, undo, audit log; instance-scoped (no globals) | `wgpu`, `glyphon`, `rubato` |
| `*-capture-{macos,windows,linux}` | Screen, window, camera, and audio sources behind one trait with timestamps mapped into the master clock | `screencapturekit`/`cidre`, `windows-capture`/`wasapi`, `ashpd`+`pipewire`, `nokhwa`/`cpal` |
| `*-encode` / `*-output` | Phase 1: FFmpeg (LGPL build) or GStreamer `appsrc` for H.264/HEVC/AAC, MP4/MKV, RTMP(S), SRT. Phase 2: native zero-copy VideoToolbox/NVENC/VA-API, WHIP | `ffmpeg-next` or `gstreamer`, `str0m`, `mp4-atom` |
| `*-web` | Browser source through CEF OSR | `cef` |
| `*-control` | REST + WebSocket JSON-RPC + MCP (stdio/HTTP) + CLI, all thin adapters over the protocol crate; optional obs-websocket-compatible shim, written from the published spec, so Companion, Streamer.bot, and existing OBS MCPs work unchanged (Rivulet's `rivulet-obs-websocket` precedent) | `axum`, `tokio` |
| GUI | Just another client of the control API | Tauri or native |

The agent-facing contract matters more than any media choice. The scene document is the single source of truth: versioned, JSON-Schema'd, and addressed by stable machine IDs with human names as labels. That fixes OBS's fragile name addressing. Mutations go through **plan → apply**. `plan` returns a structured diff, a rendered preview frame, and lint output (off-canvas items, occlusion, missing inputs, with the valid options listed). `apply` takes an `if_revision` precondition, commits atomically at a frame boundary (a `SerialFrame` batch with rollback), and returns a new revision. Apply can be scheduled (`schedule_time_ms`) or staged to Preview and then committed with an explicit `take` to Program. The MCP tool set should be small and intent-level: `get_state` (filtered or paginated), `plan`, `apply`, `take`, `preview_frame` (returns MCP `image` content for program, preview, or a source), `graphics_{add,play,next,stop}`, `diagnose_health`, and `go_live`/`stop`. Each carries the MCP `readOnlyHint`, `destructiveHint`, and `idempotentHint` annotations, and outputs are described by `outputSchema` ([MCP schema](https://modelcontextprotocol.io/specification/2025-06-18/schema)). This follows Anthropic's guidance against tools "that merely wrap existing software functionality or API endpoints" ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).

Three design constraints come from physics and safety rather than taste. First, LLM round trips take seconds while frames take 16–33 ms, so agents must author ahead of time: scheduled updates, timed transitions, and event-bound rules that the engine evaluates locally. Second, vision is a weak verifier. LiveKit samples at 1 fps (or one frame every 3 s) at 1024×1024 and warns that models misread motion ([LiveKit](https://docs.livekit.io/agents/multimodality/vision/video.md)), and Gemini Live runs at 1 fps ([Gemini](https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/models/multimodal-live)). Return structured geometry and health data alongside pixels. Third, on-air control needs rails:

- permission scopes (read, preview, program, stream-control, filesystem)
- confirm tokens for going live
- rate limits and a minimum dwell time on Program
- an operator lock and a panic "safe scene"
- stream keys redacted from all tool output
- per-subtree controller ownership with priorities, so a fast reactive agent, a slow director agent, and a human can share the show

Ship Agent Skills and an eval suite with the MCP server, as Smelter does, and keep CLI/REST parity for agents that prefer scripts.

The fastest starting sequence uses existing pieces before committing to the engine:

1. Build the protocol crate and an MCP/CLI front end that drives **stock OBS through `obws`**, with a client-side reconciler that turns plan/apply into `SerialFrame` batches. This validates tool design and evals within the licence separation, and it shows directly where obs-websocket falls short.
2. Read GodwinMix's `protocol.md`, Smelter's `smelter-core` modules (`audio_mixer`, `queue`, `timestamp`, `graphics_context`), and Cap's `crates/` layout as references. Use OBS's Backend Design doc for timing behaviour.
3. Build a single-platform headless core next. On this Mac, rec-rs and `screencapturekit` show that an all-Apple capture and encode path is practical, and libobs-rs is not an option here. Start with screen, camera, and mic, a wgpu compositor, FFmpeg RTMP and MP4 output, and `preview_frame`.
4. Point the same MCP front end at the new core. If the tools and evals pass unchanged, the abstraction is right.
5. Then add native zero-copy encoders, WHIP, CEF browser sources, multi-canvas and ISO recording, Windows and Linux backends, and WASM plugins.

## Conclusion

The gap is real, but it is not where most "Rust OBS" projects aim. Feature parity with OBS is a ten-year long tail, and the young rewrites show how fast that scope consumes a project. The open space is an engine whose state model was designed for machines first. Every agent integration found today builds dry-run, diffing, and verification on top of an imperative, name-addressed API, and every one fails at the same place: showing the model what is actually on air. An engine with revisioned declarative state, frame-atomic transactions, Preview/Program staging, and first-class rendered-frame feedback turns those workarounds into core features. That is a smaller and more defensible target than out-featuring OBS.

Two consequences follow. First, the media stack is mostly a sourcing decision: per-OS capture crates, wgpu, and FFmpeg or GStreamer get you to a credible MVP. Novel engineering concentrates in the clock and mixer, zero-copy interop, and the control contract, and only the last of those is differentiating. Second, the control contract can be proven before any pixels are rendered by running it against stock OBS. If the agent can reliably plan, preview, and take scenes on OBS through your protocol, the native engine is a back-end swap. If it can't, the engine would not have saved it.
